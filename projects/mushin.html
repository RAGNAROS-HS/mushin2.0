Mushin

This very website

active 2026-02-23

Mushin is this website: hugokatzer.tech. It is plain HTML, CSS and a few small files of vanilla JavaScript, with no framework and no theme; the only build step is a standard-library Python script that renders the Markdown writeups. What I care about more is how it gets from a commit to a running server, because that part is ordinary operations work.

How it runs

  • Image: the Dockerfile copies the static files into nginx:alpine. That is the whole container.
  • Build: on every push to main, a GitHub Actions workflow builds the image and pushes it to GitHub Container Registry, tagged both latest and with the commit SHA.
  • Server: a rented VPS runs the container with Docker Compose (compose.prod.yaml), published on port 3000. A reverse proxy in front of it terminates TLS for the domain.
  • Deploy: manual and deliberate: I pull the new image and recreate the container.
# on the VPS
docker compose -f compose.prod.yaml pull
docker compose -f compose.prod.yaml up -d

Because every build is also tagged with its commit SHA, an older version can be pinned and pulled back if a change goes wrong.

Local development

compose.yaml builds the same image locally. A compose.override.yaml, which Compose merges automatically, bind-mounts the repository into the container, so edits show up on refresh without rebuilding.

docker compose up -d --build      # dev: live files on localhost:3000
docker compose -f compose.yaml up -d --build   # the real image, no mount

The beaver

The pixel beaver, his trees and the cabin on the log are drawn in the browser from text sprite maps (pixel.js), with no image files. The beaver comes from the logo of an earlier project, Stumberg. Toggle [loud] / [quiet] in the header.

Previously, Mushin was a Hugo static site deployed by SFTP to a Cloudpanel VPS. Version 2.0 dropped the generator and moved to a container image, which is simpler to run and to roll back.
